## 0. 30 秒电梯陈述（张口就来，必须背熟）

> 我做的是一辆
>
> **两轮自平衡赛车的数字孪生**
>
> 。简单说，就是在电脑里造一辆和实物一模一样的车：
> 物理引擎（MuJoCo）算真实的重力、摩擦、电机扭矩；而车上跑的 "大脑"，不是我另外写的仿真控制器，
> 而是
>
> **真正能烧进 STM32 单片机板子的那份 C 固件**
>
> —— 它在一个叫 Renode 的芯片模拟器里运行。
> 这样带来的好处是：以前调一次参数，要改代码、交叉编译、烧板子、搬上赛道、跑一遍，几分钟还失败了不知道哪错；
> 现在改完参数在电脑里几秒就能看到结果，而且
>
> **因为跑的是同一份固件二进制，电脑上验证过的行为，就是烧到真车上会发生的行为**
>
> 。
> 最终四个比赛任务全部跑通，停车误差都在 6 厘米以内，全程零摔倒。

评委如果只甩一句 "这东西到底有啥用"，就接：

> 它解决的是嵌入式控制开发里 "烧录循环太慢、不可复现" 的痛点。仿真调参是秒级、可回放的；
> 普通仿真又不敢信，因为跑的是假控制器；我这个敢信，因为跑的是真固件。

## 1. 名词扫盲（你得先听懂自己嘴里蹦出来的词）



| 词              | 一句话人话                                                           |
| -------------- | --------------------------------------------------------------- |
| **数字孪生**       | 物理世界那辆车在电脑里的 "克隆体"，两边用同一套参数、同一份控制代码。                            |
| **MuJoCo**     | 物理引擎（DeepMind 那个）。负责 "车的身体"：重力、碰撞、轮子摩擦、电机扭矩，200 次 / 秒推进一步。      |
| **Renode**     | 单片机模拟器。它不仿真物理，它仿真的是 "那块 STM32 芯片本身"—— 寄存器、中断、外设时序。真固件二进制能在它上面跑。 |
| **STM32F407**  | 意法半导体的 ARM 单片机（Cortex-M4），智能车比赛最常用的板子。                          |
| **固件在环**       | 跑在环里的不是 "模型"，是**真正烧进芯片的那段 ELF 二进制**。                            |
| **ELF**        | 交叉编译出来的可执行文件格式，就是烧进板子的那个 .elf 文件。                               |
| **LQR**        | 一种最优控制算法。不是手调 PID，是给定权重，让数学解出一组最优反馈系数。                          |
| **互补滤波**       | 把陀螺仪（短期准、长期飘）和加速度计（长期准、短期抖）揉在一起，得到又稳又不飘的倾角。                     |
| **PID / PD**   | 经典反馈控制。这里**专门没用它**，后面会讲为什么。                                     |
| **8 路红外循迹**    | 车头一排 8 个探头，每个只输出 "压没压黑线"（0/1）。看哪几个亮，算出黑线偏左还是偏右。                 |
| **占空比 (duty)** | 电机转速指令，0\~1000 的数，正数正转、负数反转。                                    |
| **里程计**        | 数编码器走了多少脉冲，反推车走了多远。                                             |
| **三控制器槽**      | 物理侧不动，"大脑" 可以插三个版本，跑同一场景输出逐点一致。                                 |
| **build123d**  | 用 Python 代码做参数化三维建模，不是用鼠标在 SolidWorks 里画。                       |
| **法兰**         | 电机背后那个带螺丝孔的圆盘安装板。车架上要打一模一样的孔才能把电机装上去。                           |
| **GrabCAD**    | 一个免费 CAD 模型分享社区。项目里从上面下了现成零件的三维模型做视觉参考。                         |

## 2. 逐页讲稿（对着 PPT 11 页念，每页 30\~45 秒）

### P1 封面

> "这是我的项目：两轮平衡赛车的数字孪生系统。三块积木 ——MuJoCo 做物理，真实 STM32 固件在 Renode 里跑，build123d 做统一的三维模型。控制器有三个可切换的槽，后面我会展开。"

### P2 为什么要做数字孪生

> " 左边是传统实物调参循环：改代码、交叉编译、烧板子、搬上赛道、跑、失败、再改 —— 一轮几分钟，
> 而且失败了你根本不知道是参数错了、代码错了还是线没接好。右边是我这套：改 Python 参数，仿真里几秒出结果，
> 不满意立刻重试。
>
> **关键区别是：我跑的不是一个仿真出来的假控制器，而是那份真能烧进板子的固件。**
>
> "

### P3 三层架构

> " 整个系统三层，依赖是单向的。最底下 MuJoCo 是 ' 身体 '，200Hz 算物理；中间是 ' 大脑 ' 也就是控制器，
> 它只拿到原始传感器数据，只能吐电机占空比；上面是 three.js 浏览器查看器，是 ' 眼睛 '，30Hz 把状态画出来。
> 身体和大脑每 5 毫秒对话一次 —— 为什么是 5ms？因为真车 IMU 就是 200Hz 输出，仿真节拍必须和真硬件对齐。
> 安全上，车身一旦倾斜超过 55 度，立刻强制电机输出 0，防止摔车后电机疯转。"

### P4 三个控制器槽（重点页，必被问）

**讲法**：

> " 物理侧完全不动，大脑可以插三种，走的是同一个接口 
>
> `controller.step(传感器)→电机`
>
> 。
> stub 是 Python 写的桩，用来验证环境通不通；hostc 是把同一份 C 控制代码编成电脑能直接调的动态库，
> 日常调参用它，不用交叉编译；renode 是把真固件 ELF 丢进芯片模拟器跑，用来最终验证 ' 烧上去就是这个行为 '。
> 三槽同接口，同一场景跑三份，输出曲线逐点一致 —— 这就是 parity gate，它证明了电脑上调的参数等于真车行为。"

**做菜比喻（心里想，不用说出来）**：



* 菜谱就是那份 C 固件代码。

* stub = 你在游戏里炒菜，跟真菜谱没关系

* hostc = 你把餐厅菜谱拿到自家厨房炒，同一份源码

* renode = 你在餐厅后厨按菜谱炒，跑的就是那个真文件

* 三个炒出来味道一样（占空比逐点一致），就证明家里炒的等于餐厅炒的

### P5 固件在环：自研 9 个 C# 外设模型（第二重点）

**讲法**：

> "Renode 只模拟 CPU 内核，不认识我板子上具体接了什么。所以我照官方数据手册自己写了 9 个 C# 外设模型：
> MPU6050 陀螺仪、编码器、TIM1 PWM 定时器、UART 串口、ADC、I2C 总线、GPIO 电平、看门狗、时钟树 RCC。
> 信号流向是：MuJoCo 算出来的车身姿态，按真实电气协议灌进这些模型，固件读寄存器、算控制、写寄存器，
> 物理侧再把寄存器里的占空比取出来驱动电机。真车接什么线，模拟器就灌什么信号。"

**关键区分（被问才说）**：



* MPU6050 是挂在 I2C 总线上的一个器件（地址 0x68），不是总线本身

* i2c\_model 才是 STM32 芯片内部的 I2C 控制器，相当于 "收发室"

* 打比方：I2C 是走廊，i2c\_model 是你这边的收发室，mpu6050 是走廊另一门牌 0x68 的房间

**两个细节（显示你真懂）**：



1. **编码器不作弊**：不直接写计数器寄存器，而是按 20 微秒一个边沿往 A/B 引脚打真实电平跳变，让 STM32 硬件自己数。

2. **占空比要层层检查**：时钟开了吗？主输出 MOE 开了吗？方向引脚对吗？任何一个没满足，电机就是 0。这正好能抓到 "固件配置错了但自己不知道" 的 bug。

### P6 参数单一数据源

**讲法**：

> " 数字孪生最怕仿真和固件用两套参数。我的做法是 Python 参数是唯一数据源，C 头文件由脚本自动生成，人不许手改；
> 再加一道 
>
> `--check`
>
> ，改了 Python 忘了同步、或者手改了头文件，直接 exit 1 报错。
> 而且每个物理常数都标了来源 ——datasheet 的、算出来的、待实测的、明说是猜的，四类写在注释里。
> 所以仿真和固件用同一套参数这件事，是机器保证的，不是靠人记得同步。"

**底片比喻**：



* Python 参数 = 底片（唯一原件）

* .h 文件 = 洗出来的照片

* .elf = 装订成册

* 想改照片不能在照片上涂改液画，要回底片改

**.h 不是 C 固件本身**（被问才说）：



* race\_fwconfig.h 只是一张 "参数便签"，全是 `#define V_STRAIGHT 0.5f`

* 真正的 C 固件是人写的 .c 文件：main.c、race\_law.c、track.c、balance.c、stm32f4\_\*.c

* .c 文件里 `#include "race_fwconfig.h"`，然后把所有 .c 一起编译成 .elf

**P4 和 P6 什么关系**：



* P4 防的是 "三个大脑逻辑不一样"（结果对齐）

* P6 防的是 "两边参数数值抄错"（源头对齐）

* P6 是 P4 能成立的地基：参数对不上，parity gate 自然红

### P7 机械建模：build123d 单一几何源（新增页）

**讲法**：

> " 整车三维模型不是鼠标画的，是用 build123d 参数化建模，一份尺寸表同时生成两个东西：
> 给 MuJoCo 的碰撞包络体（简单盒子圆柱），和给浏览器看的视觉模型（厂商真实 STEP）。
> 这样物理和显示不可能对不上，装错位、重心偏移会立刻暴露。
> 买的现成零件从 GitHub、GrabCAD、产品尺寸图三个来源交叉验证，确认电机法兰是 6 个 M3 孔、节圆 31mm。
> 第三方模型只做视觉参考，碰撞体一律自己算，版权上也不分发。"

**两个术语解释（被问才说）**：



* **法兰** = 电机背后那个带螺丝孔的圆盘安装板。车架上要打一模一样的孔才能装上去。6 个 M3 孔 = 6 个直径 3mm 的螺丝孔，节圆 31mm = 孔分布在直径 31mm 的圆上。

* **鼠标画 vs 代码写** = SolidWorks 是用鼠标点菜单拖线条；build123d 是写 Python 变量（`length=80`），改一个数整车自动更新。好处是尺寸和仿真代码共享同一份，不会手滑抄错。

### P9 实测结果：四个比赛任务全部通过

**讲法**：

> " 跑 
>
> `uv run python -m race --all`
>
> ，四个比赛任务全过：任务 1 直线加停车，4.68 秒，限时 15 秒，停在 2 厘米内；
> 任务 2 顺时针环 18.89 秒；任务 3 交叉环 24.57 秒；任务 4 交叉环连跑 4 圈 96.64 秒。
> 停车误差全部小于 6 厘米，四个任务零摔倒，每个节点的蜂鸣序列也都对。
> 注意评分是 MuJoCo 拿地面真值打的，控制器全程只能看到和真车一样的原始传感器。"

**命令解释**（被问才说）：



* `uv run python -m race --all` = 不开窗口、纯命令行跑四个任务，自动评分，输出判决表

* 和 `bash tools/demo.sh` 的区别：这个是硬数据验证，那个是起 3D 画面给人看

### P10 3D 浏览器查看器

**讲法**：

> " 一条命令 
>
> `bash tools/demo.sh`
>
>  同时起前端网页（端口 5173）和仿真后端（端口 8766），
> 浏览器打开那个长地址就能看到 3D 实时画面。右上角实时显示倾角、位置、速度、左右电机占空比、编码器计数、电池电压；
> 左下角这 8 个灯就是循迹传感器 —— 亮的是白地板，黑的是压在线上。四个任务一键切换，还能四档倍速回放。"

**那个长地址什么意思**：



* `http://localhost:5173` = 网页本身

* `?ws=ws://127.0.0.1:8766` = 告诉网页 "仿真数据在这个地址，你去连它"

* 打比方：5173 是电视屏幕，8766 是信号源，?ws= 是选 "HDMI 1" 接口

**HUD 面板怎么读**：



* Tilt 0.08° = 车身几乎完全直立

* Pos y 100cm = 正好走了 1 米到 B 点

* Duty 0%/0% = 电机不转，停住了

* Speed 接近 0 = 没动

* Batt 11.1V = 3S 锂电池满电

## 3. 预测问答库

### A. 基础必问（送分题）

**Q：一句话说清楚你做了什么？** → 用第 0 节的电梯陈述。

**Q：数字孪生和普通仿真有什么区别？**

> 普通仿真是 "自己写个控制器糊弄一下"，和真车是两套代码，调好了也不敢烧。
> 我这个跑的是同一份固件二进制，并且三槽逐点对齐，所以电脑上的结果对真车有迁移性。

**Q：车是什么结构？怎么平衡的？**

> 两个轮子、一个直立的车身，本质是个一维倒立摆 —— 像人站在滑板上。车身往前倒，轮子就得往前追。

**Q：为什么控制频率是 200Hz？**

> 真车 IMU 典型输出就是 200~1000Hz，仿真节拍对齐真硬件时序才真实；而且倒立摆不稳定，控制律必须比车体倾倒快得多。

**Q：四个任务分别是什么？**

> 任务 1：A→B 直线停车；任务 2：顺时针绕一圈；任务 3：走对角线交叉一圈；任务 4：任务 3 路线连跑 4 圈。



***

### B. 技术深挖

**Q：用的什么控制算法？为什么不用 PID？**

> 平衡内环用 LQR。状态选了 4 个：位置、速度、倾角误差、倾角角速度。增益是在 MuJoCo 里数值线性化、解 Riccati 方程算出来的。
> **为什么不用手调 PD？**
>
>  因为轮式倒立摆手调 PD 没有稳态平衡点 —— 恒定前倾→恒定力矩→恒定加速度→车永远漂走。我一开始就栽在这。

**Q：倾角怎么测的？**

> 加速度计算倾角但车身一动就抖；陀螺仪测角速度短期准但久了会飘。用互补滤波融合：高频信陀螺、低频信加速度。

**Q：循迹怎么实现的？**

> 8 个探头每个只输出 0/1。把所有压黑的探头坐标求平均，得到黑线偏左还是偏右。
> 丢线时先保持最后误差 80ms，还丢就切里程计推算。误差限幅 ±8cm，防止猛打方向。

**Q：三个控制器槽怎么证明一致？**

> 同一个任务跑三遍，每个 5ms 周期的电机占空比存下来逐点对比：占空比漂移 0‰，轨迹偏差小于 0.1° 和 1mm。

**Q：为什么要自己写 9 个外设模型？**

> Renode 只提供通用 ARM 内核，我板子上具体接的传感器它不认识。照数据手册把寄存器行为补出来，固件一行不改就能跑。

**Q：Python 是 float64，C 是 float32，精度不一样怎么办？**

> 这是真实差异，所以才有 parity gate—— 不要求逐位相等，要求轨迹偏差在容差内。实测占空比零漂移，说明在这个尺度下差异不影响行为。

**Q：为什么用 build123d 不用 SolidWorks？**

> build123d 是代码建模，尺寸在 Python 里，改一个数整车自动更新，还能和 MuJoCo 用同一份变量。SolidWorks 改一次要手动同步三处。

### C. 质疑 / 刁难（软肋题，务必提前想好）

**⚠️ Q：仿真跑通了，真车上就一定能跑吗？**

> 这是数字孪生的核心难题。我的立场是：可信度不来自 "仿真假装很真实"，而来自每个参数都可追溯。
> 21 个关键常量分了四类标来源：8 个有 datasheet、7 个是 CAD 体积算的、3 个标了 "待上秤"、3 个是占位猜测。
> 真要上实物，把 WEIGH 那几个测了填回 Python 就行，不用改代码。
> **我承认它现在还不是 "上过真车校准" 的孪生，它是 "为上真车做好了一切接口准备" 的孪生。**

**⚠️ Q：那 8 个测试失败说明什么？为什么不装 Renode？**

> 如实说：代码路径是通的，ELF 也编译出来了（71KB/152KB），但这台 Mac 装的是桌面版 Renode，
> pyrenode3 需要 portable 的 .NET 包，所以固件在环测试在本机是 skip 状态。
> hostc 后端（同一份 C 源码编成 Mac 动态库）是完整跑通的，四个任务全绿就是证据。

**⚠️ Q：这是不是就是个仿真游戏？**

> 不是。评分器拿 MuJoCo 内部地面真值打分，但控制器只能看到和真车一样的原始传感器（int16 加速度、编码器计数）。
> 它拿不到物理引擎内部状态，不是开卷考试。而且产出物是一份能直接烧进 F407 的 ELF。

**⚠️ Q：你自己做了多少？**

> MuJoCo、Renode、three.js 是现成引擎。我自己写的是：整车物理建模与 LQR 推导、9 个外设 C# 模型、
> 三槽 parity 对齐、参数单一源与 check 门、循迹状态机、评分器、227 个测试、从 CAD 到物理到查看器的整条管线。

**⚠️ Q：最大困难是什么？**

> 一开始平衡车一直漂。我以为是 PID 没调好，调了很久没用。后来才想明白轮式倒立摆手调 PD 根本没有稳态平衡点。
> 这逼着我去读线性化和 LQR 理论，把系统在 MuJoCo 里数值化、解 Riccati 方程，漂移才解决。
